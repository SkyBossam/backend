# 11. 테스트·구현 순서

## 필수 인수 시나리오
1. 개인 계정 생성 시 PERSONAL 워크스페이스가 생성된다.
2. 기관 멤버가 되어도 개인 공간의 아이 정보를 자동 조회할 수 없다.
3. 보호자가 시터 초대 시 아이 A의 `cry:read`, `cry:feedback`만 주면 아이 B와 영상 접근은 거부된다.
4. 시터 초대 만료/철회 시 API·실시간 구독·스트림 접근이 차단된다.
5. 다른 기관의 `workspace_id`/`child_id`를 임의로 넣어도 접근할 수 없다.
6. 기관-보호자 공유 철회 후 이미 열린 세션의 정보 조회가 실패한다.
7. 미연결 카메라·가려진 영상은 `unknown`/`unverifiable`이며 `stable`로 나오지 않는다.
8. 위험 알림 읽음, 모달 열기, ‘확인하러 가기’는 `resolved`로 바뀌지 않는다.
9. `needs_help` 제출은 자동으로 해결 완료하지 않는다.
10. 울음 추천 실패/대기 중에도 안전한 기본 확인 안내가 반환된다.
11. 울음 피드백 중복 POST는 멱등 응답으로 한 번만 저장된다.
12. `hunger` 원인 후보를 선택해도 수유 전용 테이블/기록이 생성되지 않는다.
13. 추천 행동 시도 여부와 반응은 별도 필드이며 '미시도'도 저장 가능하다.
14. 구독자가 온라인이 아니어도 재연결 시 새 이벤트를 REST로 재조회한다.
15. 다중 아동 홈은 위험도 순으로 정렬한다.
16. 알림/이력/집계 API도 동일한 아이별 권한을 적용한다.

## 개발 단계
- P0: 사용자/공간/아이/멤버/권한 + DB + 인증/감사
- P1: 루틴, 감지 이벤트, 대시보드, 상태 전이
- P2: 울음 추천·피드백, 알림/SSE
- P3: 기관 연결, 데이터 공유 동의·철회, 시터 초대
- P4: 실제 영상 연동, 추론 모델·센서, 장애·부하 테스트

## 프론트 연계
기존 `data-contracts.md`와 핵심 enum을 맞춘다. 추가 필드:
- REST마다 `workspaceId` 컨텍스트
- `membershipId`, `capabilities`, `validUntil`
- `streamStatus=unverifiable`, `sensors[].connected=false`
- `detection.status` 및 별도 per-user `acknowledgedAt`
기존 FE 경로는 유지하고 관리/초대 화면은 필요 시 하위 페이지 확장.
